# riskelle

A deterministic risk score for every code change, so developers and agents can
see — before, during and after the work — how risky a change is, and aim to make
each one smaller.

## Install

```sh
curl -fsSL https://github.com/bobmcallan/riskelle/releases/latest/download/install.sh | sh
```

It installs the latest release for Linux or macOS (amd64 or arm64) into
`~/.local/bin`, after checking the archive against the release's checksums
file, and prints the installed version. `RISKELLE_VERSION=vX.Y.Z` pins a
release and `RISKELLE_INSTALL_DIR` picks the directory, both in front of `sh`
(`… | RISKELLE_VERSION=vX.Y.Z sh`); the header of
[`scripts/install.sh`](scripts/install.sh) documents the rest.

Or build it from source with the Go version in `go.mod`:
`go install github.com/bobmcallan/riskelle/cmd/riskelle@latest`, or
`go build -o ~/.local/bin/riskelle ./cmd/riskelle` from a clone. A build from
a clone reports its version as `dev`; release builds are stamped by
`scripts/release.sh`.

## Intent

Risk is about **the change itself**: how big it is, how much existing code it
alters, how far it reaches and how long it stayed away from the trunk. Every one
of those is in the hands of the person (or agent) making it.

Low risk is focused development: the smallest change with the lowest impact,
merged quickly. Many small stories are better than one large one.

The level says what it takes to put a change right if it goes wrong:

- **Low** — small, tested and revertible.
- **Medium** — risky, but a revert of the merge puts it right.
- **High** — destructive: hard or impossible to undo, or harm to production,
  customers, their data or security. A revert does not put it right.

Volume alone is never destructive. The shape of a change (its size, spread,
degree, impact, branch age and untested files) scores the total in full, but
its level caps at Medium. High comes only from a consequence whose floor is
High (see [Consequences](#consequences)).

The score is the fundamental measure for developers. Each developer's KPI is the
share of their changes that are low risk, so the score must be:

- **Deterministic** — the same change always gets the same score. No LLM in the
  scoring path.
- **Transparent** — every point names the measure and the facts behind it, and
  anyone can re-run it locally and get the same number.
- **One scale** — the same bands for every repo and team, so percentages compare.
- **Not lowerable from inside a change** — a pull request cannot change the
  rules that score it.

## Measures

| Measure | What it captures |
| --- | --- |
| Size | Lines added and removed, excluding generated files, lock files (such as `go.sum`, `package-lock.json`, `packages.lock.json`, `*.lock` and `.terraform.lock.hcl`), docs and tests, deleted files nothing at head depends on, and by default non-code files and run records (see [Rules](#rules)) |
| Spread | Files, directories and projects (`go.mod`, `package.json`, `.csproj`) touched; a renamed file counts in its new directory only |
| Degree | How much *existing* code is altered, against code in new files (tests are left out, as for size, as are deleted files nothing depends on, and by default so are non-code files and run records) |
| Impact | How many places depend on what changed (for Go, packages importing a changed package; otherwise files referencing a changed file) |
| Branch age | Days from the branch's first commit to merge, and how far the trunk moved meanwhile |
| Tests | Production code files changed without their paired test (see [Tests and their pairs](#tests-and-their-pairs)); a Shell or Terraform file (an extensionless script whose first line is a shell shebang included) counts only when no test changed and the repo holds a test in its language; any other file (YAML, JSON, XML, other config or data, an extensionless file with no shell shebang) is not code and never counts (see [Which files count](#which-files-count)); a deleted file nothing depends on never counts |

A file is generated when its path matches a built-in or repo-added generated
pattern, or when its header carries a marker. The header is the comment lines
(starting `//`, `/*`, `*`, `#`, `<!--`, `--` or `;`) among the first 20 lines
of its blob at head, ending at the first code line. The markers, matched
case-insensitively, are `do not edit`, `do not modify`, `@generated` and
`<auto-generated`. A deleted file is classed by its path only.

A deleted file that nothing at head depends on is not code anything still
relies on. When its impact entry (for a Go file, its package's entry) has 0
dependents, it is left out of size, degree and tests and listed in size's
excluded paths. A doc naming a deleted file does not rely on it either: a
deleted file that impact counts as a file is left out the same way when every
file at head that refers to it is in the docs class (a README saying it was
removed, a ticket note). Any other referrer (code, config, tests) keeps it
counting in full, as do a Go package with dependents and a deleted file with no
impact entry. Spread, impact and consequences still see every deleted path, and
impact still counts every referrer, docs included, so a floor on a deleted path
still floors. The facts mark such a file `"deleted": true`, name a Go file's
package import path in `"package"`, and list the head paths that refer to any
other deleted file in `"referrers"`.

Each measure scores points in fixed bands; the total is 0–100. The band edges
are calibrated from real merge history before anyone is measured. The total's
own level, the shape level, is Low or Medium: it caps at Medium (`shape_cap` in
the built-in rules), so a total in the High band keeps every point and every
breakdown entry and reports Medium. A consequence (below) can raise the
reported level to its floor, and only a High floor makes it High; it never
changes the total.

Where a change lands (auth, migrations, infrastructure, secrets) is shown on the
report as context for reviewers, but does not count towards the score: it is the
area's risk, not the developer's (see [Sensitive areas](#sensitive-areas)).

### Consequences

A consequence is what a change *does*, read from its changed lines, not where
it lands. riskelle finds each consequence class in a built-in, versioned
catalog, mechanically and the same way every time, and records it in the facts
as `"consequences"`: the class, the paths that triggered it and the block types,
pipeline keys, commands, destructive operations or secret rules that did.
`stateful_destroy` is read from the resource blocks a directory declares at
each side, not from changed lines (see **Stateful destroy** below). A changed
pipeline definition also records the job environments it names as
`"environments"` on its file, from which score reads `production_deploy`.

Each class sets a **floor**: the reported level is the higher of the shape
level (the total's own level, capped at Medium) and every consequence's floor. A floor never changes the total or any
breakdown entry, so the shape score still rewards small changes, and splitting a
change cannot lower a floor: the class lands in whichever change carries it.
The report gives the shape level as `"shape_level"` beside the level (see
Report).
The floors are built in (`consequence_floors`), recorded in the rules hash on
every report, and refused by name if `.risk/rules.json` sets them: a repo can
only raise a floor, through production roots.

**Production roots.** `.risk/rules.json` may name `production_roots`: globs for
directories, each ending in `/**` (such as a production tenant's Terraform
root). A consequence whose triggering path lies under one (at head, at the
merge base for a rename or deletion, or a planned path) is floored at High, the
top of the scale, instead of its class's floor; the consequence names the
roots. The total is unchanged. Roots are read from the target branch like every
rule, recorded in the rules hash, and change nothing for a change with no
consequence in them.

**Repo classes.** Which files are guards, allow-lists or enrolment lists is
repo knowledge no built-in catalog can know, so `.risk/rules.json` may name its
own classes under `consequence_classes`: a class name, its path globs and a
floor of Medium or High, such as
`{"consequence_classes": {"release_guard": {"paths": ["scripts/plan-guard-allow*"], "floor": "Medium"}}}`.
A changed or planned path matching a class's globs carries it (a rename is
checked at its old path too); the class is read from the path alone, so its
`types` is `[]`. A production root raises it to High like any class. It is
recorded in the rules hash and listed in the report's consequences like the
built-in classes. A built-in class name, a `Low` or unknown floor, and an empty
or absolute glob are refused by name: a repo class can only raise the level.

- Delivery rights count as identity and rights: Azure DevOps and GitHub service
  connections and their authorisations, deployment environments and their
  checks, branch policies and protections, and permissions decide who can act
  as a deploy identity. Service connections and permissions are identities
  and what they may do; the rest are delivery gates (below). Generic secrets
  and variables
  (`github_actions_secret`, `azuredevops_variable_group`) do not.
- Group membership counts too: who is in a group decides who holds the roles
  granted to it, as a role assignment does.
- For a type listed with attributes, a block carries the class only when a
  changed line falls in one of those attributes at the block's top level: the
  argument line and every line of its multi-line value (a list, a function
  call or a heredoc) up to its closing bracket. The attribute column is the
  indent of the block's first indented line. Blank lines, comments between
  attributes, other arguments (such as `description` or `display_name`) and
  nested blocks (such as `lifecycle`) carry none.
- For `identity_rights`, only `.tf` and `.tfvars` files are read, and in them
  only `resource` and `data` blocks of a catalogued type. A mention of a type
  in any other file never counts.
- A changed variable carries the classes of the blocks that use it. A changed
  line sets variable `X` when it is an `X = …` assignment (or its multi-line
  value) in a `.tfvars` file (not `.tfvars.json`), or a line in any top-level
  attribute except `description` of a `variable` block (`variable "X"`) in a
  `.tf` file.
  It carries every class of the catalogued `resource` and `data` blocks in the
  `.tf` files of the same directory, read at the same side's commit, with a
  line referencing `var.X` (for a type listed with attributes, the line must
  fall in one of them). The consequence names the changed variable file and
  the type as `<type> via var.X`. A `description`-only change, blank lines and
  comments carry nothing. Only the same directory is read: module inputs,
  `-var-file` files elsewhere and `locals` indirection are not traced, and the
  match is textual (full-line comments are skipped).
- A block carries its class when any line in it is added, removed or altered:
  added lines are read at head, removed ones at the merge base. A rename is
  checked at both paths.
- A line added at head (an altered line is one removed and one added) that
  carries `identity_rights` carries `access_widened` too, floor High, with the
  same path and type, `<type> via var.X` included: a grant added or altered
  makes the change High. A change whose `identity_rights` lines are all
  removed ones (a grant, a member or a `.tfvars` assignment removed) carries
  `identity_rights` alone and stays Medium. Any other added line in a
  catalogued block counts, and what the value grants is not read, so removing
  a restricting line (a condition or a deny) is a removed line and stays
  Medium.
- A label does not widen. A line in a block's `description` or `display_name`
  attribute, and a variable used only there, carries `identity_rights` but
  never `access_widened`: it says what the block is for, not what it grants.
  `display_name` is no label where it decides access: in a `data` block it
  selects the object read (which principal a grant targets), and in
  `azuread_directory_role` it names the role.
- A delivery gate does not widen. The gates are
  `azuredevops_pipeline_authorization`, `azuredevops_resource_authorization`,
  `azuredevops_environment*`, `azuredevops_check_*`,
  `azuredevops_branch_policy_*`, `github_repository_environment*`,
  `github_actions_environment_*`, `github_branch_protection*`,
  `github_repository_ruleset` and `github_organization_ruleset`, but never a
  `*_permissions` type. Which pipeline may use an environment or resource,
  the environment, its checks, policies, protections and rulesets take effect
  only when a pipeline then runs, and a revert of the merge puts them back:
  a line in one, or a variable only a gate uses, carries `identity_rights`
  (Medium) but never `access_widened`. Adding a check is a restriction. What
  a gate guards is not read (an environment is often a bare id), so a Dev and
  a production environment read the same; a change to a pipeline that deploys
  to production is already `production_deploy`, and a repo that wants its
  production gates High names a production root or a repo class over those
  paths.
- A restyle is not a change. In a `.tf` or `.tfvars` file, a removed line and
  a later added line of the same hunk that differ only in whitespace outside
  a string or in a trailing `#` or `//` comment are the same line, as when
  `terraform fmt` realigns an assignment: neither counts at either side. A
  blank line and a full-line comment carry nothing. Two limits: a heredoc
  body line is compared the same way, so a whitespace or trailing-`#` change
  inside a script heredoc counts as no change; and a line inside a
  multi-line `/* */` comment is read as code.
- Blocks are found by their header at column 0, as `terraform fmt` writes every
  file; a heredoc body (such as a JSON policy) belongs to its block wherever it
  starts. A file that is not formatted may be misread.
- A plan has no content, so a planned path names its classes instead (see
  [Plan file](#plan-file)).

**Stateful destroy.** `stateful_destroy` is a stateful resource removed:
databases and servers, storage accounts, containers, shares and buckets, key
vaults and their keys, secrets and certificates, DNS zones, caches, message
namespaces, log workspaces, recovery vaults and KMS keys, across `azurerm`,
`aws` and `google`, whose destruction loses data a revert does not bring back.

- A `resource` block of a catalogued type carries it when its address
  `type.name` is declared in a `.tf` file of directory D at the merge base and,
  at head, no `.tf` file of D declares it, names it as the `from` of a `moved`
  block, or names it as the `from` of a `removed` block. Only the directories
  of the merge-base paths of changed `.tf` files are read.
- The consequence names the merge-base path of the file that declared the
  block and the resource type, so a production root on a deleted path still
  floors.
- Nothing is carried by a block moved to another file of the same directory,
  a `moved` block whose `from` is the address (a rename), a `removed` block
  whose `from` is the address, a `data` block, an uncatalogued type, or an
  edit to the block.
- Limits: Terraform plan JSON is not read (it is not in git and needs
  credentials). An in-place replace, a lower `count` or `for_each`, and
  `prevent_destroy` are not read. A `removed` block exempts the address
  whatever its `lifecycle` says, `destroy = true` included. A block moved to
  another directory counts as removed from its own. A `from` naming an
  instance (`type.name[0]`) or a module address exempts nothing. `.tf.json`
  files are not read.

**Pipeline definitions.** `pipeline_identity` is what decides which code runs
as an identity: a CI/CD pipeline that names a service connection or deploys to
an environment. A file is a pipeline definition when its path matches one of
`.github/workflows/*.yml`, `.github/workflows/*.yaml`, `**/azure-pipelines*.yml`,
`**/azure-pipelines*.yaml`, `.azuredevops/**/*.yml`, `.azuredevops/**/*.yaml`,
`**/pipelines/**/*.yml`, `**/pipelines/**/*.yaml`, `**/.pipelines/**/*.yml`,
`**/.pipelines/**/*.yaml`, `**/azure-pipelines/**/*.yml`,
`**/azure-pipelines/**/*.yaml`, `**/.azure-pipelines/**/*.yml`,
`**/.azure-pipelines/**/*.yaml`, `**/templates/**/*.yml` or
`**/templates/**/*.yaml`, **and** it has one of these keys at column 0:
`jobs`, `stages`, `steps`, `extends`, `trigger`, `pr`, `resources`,
`schedules`, `variables`, `parameters` or `on` (a docker-compose or Helm file
has none). Azure Pipelines templates conventionally live in a `templates/`
folder; a Helm chart's `templates/` has none of these keys at column 0 and no
catalogued key, so it carries nothing.

- A changed line carries the class when its key, or a key it is nested under,
  is a catalogued key. Keys match case-insensitively, and the consequence's
  types are the keys as written (such as `azureSubscription`).
- `environment` counts only on a job: a direct key of an Azure `- deployment:`
  item, or `jobs.<job_id>.environment` in a GitHub workflow; never under
  `variables:`, `env:` or `with:`.
- A changed reference to the code a pipeline runs carries the class only when
  that side's content (head for added lines, the merge base for removed ones)
  carries a catalogued key on some line: a repository resource's `ref`
  (`resources.repositories[].ref`), `extends: template:` (an `@repo` suffix
  included), and a `template:` that is a direct key of a list item under
  `stages:`, `jobs:` or `steps:`, each typed by its key path. A definition with
  no catalogued key carries nothing for them. A repository's `name`, a
  `variables:` template and GitHub `uses:` are not read.
- Comments and block-scalar content (a `script: |` body) are never read as
  keys. Added lines are read at head and removed ones at the merge base.
- It is an indentation walk, not a YAML parser: flow style
  (`permissions: { id-token: write }`) and list-form variables
  (`- name: azureSubscription`) are not read, and an Azure `deployment` must be
  its list item's first key.

**Production deploys.** `production_deploy` is a change to a pipeline that
deploys to production, floor High: what such a pipeline runs, runs against
production, so any changed line counts, a script line, a comment or a blank
line included.

- A job environment is the `environment` that `pipeline_identity` reads (a
  direct key of an Azure `- deployment:` item, or `jobs.<job_id>.environment`
  in a GitHub workflow), named by its scalar value or by the `name:` directly
  under its mapping form.
- It names production when, ignoring case, it is `prd`, `prod` or
  `production`, or starts with one followed by a character that is not a
  letter (`prd-aue`, `prod_eu`, `production.web`); `product`, `pre-prod` and
  `nonprod` do not. The consequence's types are the environment names as
  written. The names are built in and recorded in the rules hash;
  `.risk/rules.json` may name more under `production_environments`, read from
  the target branch and recorded in the rules hash, but cannot remove a
  built-in one.
- Each side a definition changed on is read: head when the change adds a line
  to it, the merge base when it removes one, so changing `prd` to `dev` still
  carries the class.
- A templated name (`${{ parameters.environment }}`) is not traced to its
  caller, and a name that ends in a production name (`aue-prd`) does not
  match.
- A deploy to `dev` or `test` carries no `production_deploy`: a changed
  catalogued line carries `pipeline_identity` alone, at Medium. Splitting a
  change cannot lower the floor: the class lands in whichever change touches
  the definition.

**Definition writes.** `definition_write` is a script that writes a release or
build definition out of band, through the Azure DevOps REST API or CLI. It is
floored at High: reverting the merge does not undo a write the script already
made.

- Every changed file that is not binary, not docs and not a test (class
  `test`, as Which files count decides it) is read, whatever its extension (a
  `.sh`, a `.ps1`, a pipeline's inline script). Docs and test files that
  spell the command carry nothing: a fixture is data a test asserts on, not a
  script that runs.
- Only added lines count, read at head: removing a write command writes
  nothing. A changed line carries the class when the logical command it
  belongs to is a write: a line and each following line while the line ends
  in a backslash, joined. A change to any one continuation line of the
  command counts; a change to a line beside an unchanged write does not.
- The command may sit anywhere in the logical line, such as inside `$(...)`.
  A full-line comment (first non-blank character `#`) carries nothing and
  ends a continuation; a read of the same definition (a `GET`, or no
  `--http-method`) carries nothing.
- The type is the command and its method, such as
  `az devops invoke --area release --http-method PUT`, `az pipelines update`
  or `curl PUT _apis/build/definitions`.
- It is a textual match, not a shell parser: a URL or method held in a
  variable, `curl`'s implied `POST` (`-d` with no `-X`), PowerShell backtick
  continuations and a command split across lines without backslashes are not
  read.

**Destructive migrations.** `destructive_migration` is a change that drops,
truncates, deletes or renames data: once it runs, the data is gone. Its types
are the operations matched, as listed above.

- A migration ships to every environment, so the floor is High everywhere: it
  is not narrowed to production roots, and a root only adds its name.
- Only added lines are read, at head: an altered line is an added line, and a
  removed line or a deleted file carries nothing. Removing a destructive
  statement makes a change safer.
- An EF Core migration is a `.cs` file under a `Migrations` directory, and a
  SQL file ends in `.sql` (both case-sensitive). Its `Down` method is not read:
  `Down` is the rollback, and scaffolding writes a drop there for every
  additive migration. `Down` runs from its `void Down(` line to the first later
  line that is only `}` at that line's indent or less; a one-line `Down` (a
  line ending in `}` or `;`) covers only itself. Code after it, helpers
  included, is read.
- A builder call counts on the call's own line, on a parameter named
  `migrationBuilder` (`migrationBuilder.DropColumn(`), matched case-sensitively.
  `AddColumn`, `CreateTable`, `DropIndex` and `DropForeignKey` carry nothing.
- SQL statements count in a `.sql` file and on every read line of a migration
  (the SQL of `migrationBuilder.Sql(...)` often sits on later lines of a
  multi-line string), case-insensitively, with the keywords on one line.
  `TRUNCATE` counts only when not followed by `(`, so `Math.Truncate(x)` and
  MySQL's `TRUNCATE(x, d)` do not. `ALTER TABLE ... DROP` counts on any line
  of the statement that carries `DROP`, up to the statement's `;` or a blank
  line, so `ALTER TABLE t` then `DROP CONSTRAINT c;` counts;
  `ALTER TABLE t DROP COLUMN c;` reports both `ALTER TABLE DROP` and
  `DROP COLUMN`.
- Comments are never read: `/* */` (across lines) and `--` to the end of the
  line in both kinds of file, and `//` to the end of the line in a migration.
- It is a line walk, not a C# or SQL parser: quoted text is read as SQL, a
  comment marker inside a string starts a comment, and a builder under another
  name is not read. SQL renames (`sp_rename`, `RENAME TO`) and other migration
  frameworks are not read.

**Added secrets.** `secret_added` is a secret committed to the repository: a
revert does not unleak it, it has to be rotated, so its floor is High. Each
rule matches within one line, by a fixed prefix and the real token's length,
so a shorter placeholder does not match:

- `aws_access_key_id`: `AKIA` or `ASIA` followed by exactly 16 upper-case
  letters or digits, with no letter or digit on either side.
- `azure_storage_account_key`: `AccountKey=` followed by 86 or more base64
  characters.
- `github_token`: `ghp_`, `gho_`, `ghs_` or `ghu_` followed by 36 or more
  letters or digits, or `github_pat_` followed by 82 or more letters, digits or
  underscores.
- `google_api_key`: `AIza` followed by 35 letters, digits, `_` or `-`.
- `private_key`: a PEM header of five dashes, `BEGIN`, any upper-case words
  (`RSA`, `EC`, `OPENSSH`, `ENCRYPTED` or none) and `PRIVATE KEY`, or the PGP
  `PRIVATE KEY BLOCK` form, then five dashes. Public keys and certificates do
  not match.
- `slack_token`: `xoxa-`, `xoxb-`, `xoxp-`, `xoxr-` or `xoxs-`, a numeric id,
  `-` and 10 or more letters, digits or `-`.

What is read, and what is reported:

- Only lines added at head are read, from the head blob: a removed line, an
  untouched line of a modified file, a deleted file and a pure rename carry
  nothing; an altered line that still holds the secret counts.
- Every text file is read, whatever its class (docs, tests, generated, lock or
  vendored); a file git reports binary, a symlink and a submodule are not.
- There is no allow-list and no entropy or validity check: a full-length
  lookalike floors. Write a placeholder shorter than the rule, or build a test
  sample at runtime.
- The consequence names the path and the rule; the matched text is never in
  the facts or the report.
- It is not the `secrets` sensitive area, which is read from paths alone and is
  reviewer context only (see [Sensitive areas](#sensitive-areas)).

### Test files

The tests measure classes a file as a test from its path alone, by the built-in
catalog below. The catalog is versioned with each release and owned by
`internal/facts/classes.go`. Patterns are case-sensitive globs over the
repo-relative path, and `**/` matches any directories.

| Language | Test paths |
| --- | --- |
| Go | `**/*_test.go`, `**/testdata/**` |
| JavaScript/TypeScript | `**/*.test.*`, `**/*.spec.*`, `**/__tests__/**`, `**/__mocks__/**`, `**/__snapshots__/**` |
| .NET | `**/*Tests/**`, `**/*Test/**`, `**/*Tests.cs`, `**/*Test.cs` |
| Python | `**/test_*.py`, `**/*_test.py`, `**/conftest.py` |
| Java/Kotlin | `**/*Test.java`, `**/*Tests.java`, `**/*Test.kt`, `**/*Tests.kt`; `src/test/**` by `**/test/**`, `src/androidTest/**` and `src/integrationTest/**` by `**/*Test/**` |
| Ruby | `**/spec/**`, `**/*_spec.rb`, `**/*_test.rb`; `test/**` by `**/test/**` |
| Rust | `tests/**` by `**/tests/**` |
| PHP | `**/*Test.php` |
| Swift | `**/*Tests.swift`; `*Tests/**` by `**/*Tests/**` |
| C/C++ | `**/*_test.c`, `**/*_test.cc`, `**/*_test.cpp`, `**/*_unittest.cc`, `**/*_unittest.cpp` |
| Scala | `**/*Spec.scala`, `**/*Suite.scala`, `**/*Test.scala` |
| Elixir | `**/*_test.exs` |
| Dart | `**/*_test.dart` |
| Terraform | `**/*.tftest.hcl`, `**/*.tftest.json` |
| Shell | `**/*.bats`; script tests named `x-test`, `x_test` or `test-x`, with no extension or `.sh`/`.bash` (such as `scripts/plan-guard-test`, `run-test.sh`) |
| Any ecosystem | `**/test/**`, `**/tests/**` |

- In-file unit tests (Rust `#[cfg(test)]`, Python doctests) cannot be seen from
  a path.
- Any directory named `spec/` or `test/` is classed test whatever the language.
- Shell script test names are matched in `internal/facts/pairs.go`, not by a
  glob: a glob cannot say "no extension", and `**/test-*` would class
  `src/test-utils.ts` as a test too. An extensionless name has no dot, so
  `v1.2-test` is not one.

### Tests and their pairs

Each test file names the production file it tests, from its file name alone.
The tests measure counts a production file as tested when a changed test pairs
with it. The rules are owned by `internal/facts/pairs.go`; for a file `x`:

| Language | Production files | Test names |
| --- | --- | --- |
| Go | `.go` | `x_test.go` |
| Python | `.py` | `test_x.py`, `x_test.py` |
| .NET | `.cs` | `xTests.cs`, `xTest.cs` |
| JavaScript/TypeScript | `.js`, `.jsx`, `.mjs`, `.cjs`, `.ts`, `.tsx`, `.mts`, `.cts` | `x.test.js`, `x.spec.js` (same extension as the file) |
| Java/Kotlin | `.java`, `.kt` | `xTests.java`, `xTest.java` (same extension) |
| Ruby | `.rb` | `x_spec.rb`, `x_test.rb` |
| PHP | `.php` | `xTest.php` |
| Swift | `.swift` | `xTests.swift` |
| C/C++ | `.c`, `.cc`, `.cpp` | `x_unittest.cc` (`.cc`, `.cpp` only), `x_test.c` (same extension) |
| Scala | `.scala` | `xSpec.scala`, `xSuite.scala`, `xTest.scala` |
| Elixir | `.ex` | `x_test.exs` |
| Dart | `.dart` | `x_test.dart` |
| Shell | `.sh`, `.bash`, no extension | `x-test`, `x_test`, `test-x` (same extension as the script, or none) |

- Directories are ignored, so a test in another directory still pairs; two
  files with the same name in different directories are both paired by one test.
- Names are case-sensitive and the extension must match (`a.ts` pairs with
  `a.test.ts`, not `a.test.js`), except Elixir, whose `.exs` tests test `.ex`
  code.
- The first matching name in the table wins, so `test_x_test.py` pairs with
  `x_test.py`.
- A test file with no naming marker (`__tests__/a.js`, `tests/api.rs`, a file
  in a `*.Tests` project, a fixture under `testdata/`) pairs with the file of
  its own name.
- Terraform and Rust have no file pairing: a Terraform test exercises a module
  directory, and Rust unit tests sit inside the file they test while its
  `tests/` files are named by feature. A `.bats` file has no fixed subject.
  C/C++ headers (`.h`, `.hpp`) are not paired either.
- A Shell script test names its script (`scripts/plan-guard-test` tests
  `scripts/plan-guard`), but scripts are scored by the Shell rule below: a
  `.sh` or `.bash` script, or an extensionless one whose first line is a shell
  shebang. An extensionless script with no shell shebang names no language and
  never counts as untested.

#### Which files count

- A file in a paired language (the table above) counts as untested unless its
  test changed.
- A Shell or Terraform file counts under the rule and table that follow.
- Every other file never counts.

A Shell or Terraform file cannot be paired with one test, so it is judged by
whether the repo can test it at all. It counts as untested only when no test
changed **and** the head tree holds at least one test in its language. In a
repo with no tests in that language, a test cannot be asked for: splitting the
change would be the only way down, which buys no safety.

| Language | Production files | Its tests |
| --- | --- | --- |
| Shell | `.sh`, `.bash`; an extensionless file with a shell shebang | `.bats` |
| Terraform | `.tf`, `.tfvars` | `.tftest.hcl`, `.tftest.json` |

- An extensionless file is a Shell script when its first line at head is a
  shell shebang: `#!` then `sh`, `bash`, `dash`, `zsh` or `ksh`, by path
  (`#!/bin/bash`) or through `env` (`#!/usr/bin/env bash`). Any other first
  line, none, `python3` or `node`, names no language. A file with an extension
  is judged by its extension alone. The line is read in the same pass as
  generated headers; a deleted file has none.
- A file the catalog classes test with the language's extension (such as
  `tests/smoke.sh`) also counts as a test in that language.
- A Shell script test (`x-test`, `x_test`, `test-x`), extensionless included,
  counts as a Shell test whatever its first line, so a repo of extensionless scripts with their tests
  holds Shell tests.
- Any other file is not code that riskelle can test: YAML (pipelines included),
  JSON, XML, TOML, other config and data, extensionless files with no shell
  shebang (a `Makefile`, a `Dockerfile`, a Python or Node script, data files), and languages with no row above
  (Rust, C/C++ headers). It never counts as untested. It still counts for
  size, spread and degree; what it touches is the consequence axis's concern
  (see [Consequences](#consequences)).
- The facts carry the languages found as `"test_languages"`, read from the
  head tree. A change cannot lower its own count: deleting a repo's tests is a
  test change, and adding one only raises the count.

## Estimate, then score

The same scorer runs over two sources of facts:

- **`riskelle estimate`** — at planning, from the files the plan says it will
  change, the expected size and the target branch age. Most of it is exact (the
  planned paths give spread and impact); size is the guess. A high estimate is
  the cheapest point to split a story.
- **`riskelle score --base <ref> --head <ref>`** — the real diff. Run locally
  while working to bring the score down, and in CI on every pull request (or
  push) as the official figure.

### Plan file

`riskelle estimate plan.json`, run in the repository the change targets, reads
a JSON plan file that predicts the change:

```json
{
  "target": "main",
  "branch_age_days": 1,
  "files": [
    {"path": "internal/facts/plan.go", "added": 110},
    {"path": "cmd/riskelle/main.go", "added": 40, "removed": 2},
    {"path": "internal/facts/plan_test.go", "added": 95}
  ]
}
```

- `target` (required): the branch the change will merge into. Its tree says
  which planned paths are new (new files, and so new packages), holds the
  project manifests, and is where impact is counted and `.risk/rules.json` is
  read, as for a real score.
- `files` (required, not empty): every path the change will touch, each listed
  once, repo-relative, slash-separated and clean (no leading `/`, no `..`).
  - `added`, `removed`: expected line counts, non-negative. At least one must
    be given; an absent one is 0.
  - Planned tests are the test files listed (they are classed from the path,
    as in a real diff, and their lines are left out of size and degree).
  - A planned path that exists at the target is read there: it is also classed
    generated when its header carries a marker, and an extensionless one is a
    Shell script when its first line is a shell shebang. A new extensionless
    path has no content, so it names no language (see
    [Which files count](#which-files-count)).
  - A move is its old path with the removed lines plus its new path with the
    added lines.
- `branch_age_days` (optional, default 0, non-negative): the expected days
  from the branch's first commit to merge.
- `consequences` (optional, per file): the consequence classes the path is
  expected to carry, such as `{"path": "iam/roles.tf", "added": 20,
  "consequences": ["identity_rights"]}` or `{"path": "pipelines/release.yml",
  "added": 40, "consequences": ["pipeline_identity"]}` or
  `{"path": "db/migrations/002_drop.sql", "added": 3, "consequences":
  ["destructive_migration"]}`; see
  [Consequences](#consequences). A planned path that adds or alters a grant
  names both, `"consequences": ["identity_rights", "access_widened"]`. A
  planned change to a pipeline that deploys to production names
  `"production_deploy"`, and a planned path that removes a stateful resource
  names `stateful_destroy`. An
  unknown class, or one listed twice for a path, is refused by name. It names
  built-in classes only: a repo class is found from the planned path, by the
  globs in the target's rules, as for a real diff.
- Which languages have tests (see [Which files count](#which-files-count))
  is read from the target's tree plus the planned paths; the plan file has no
  field for it.

Any other field is refused. Trunk drift cannot be planned and is 0. A plan
that is invalid or incomplete is refused with every problem named, exit code 1.

It prints the same report as a real score, marked `"kind": "estimate"` and
naming the plan file in `"plan"`.

### Report

`riskelle score` and `riskelle estimate` print their report as JSON by
default, or as a Markdown summary for a PR comment with `--format markdown`
(flags go before the plan file). Both carry the total and level, every
breakdown entry with the facts behind it, and the provenance (riskelle
version, rules source, rules commit and hash, and the two exclusion toggles). A score names the full base
and head commits it measured (`"base"`, `"head"`); an estimate is marked as
one and names its plan file. The sensitive areas the change lands in sit apart,
under `"context"` (JSON) or "Where it lands (context, not scored)" (Markdown),
labelled as context that does not count towards the score. The consequences the
change carries sit under `"consequences"` (class, paths, types and floor; `[]`
when none) and, in Markdown, under "Consequences (floor the level)", shown only
when there is one. A consequence floored by a production root carries
`"production_roots"`, and its Markdown line reads `floor High (production root
…)`. A `secret_added` consequence's types are its secret rule names; the report
never contains the matched text. Every report also carries `"shape_level"`, the level of the total
alone, beside `"level"`; it never exceeds Medium, whatever the total.
`"level"` is High only when a consequence's floor is High. When a consequence
floor raises the level above the shape level,
`"floored_by"` names the classes whose floor set it (`[]` otherwise), and the
Markdown opens with a line stating the shape level, the floor that set the
level and that splitting the change will not lower it. A flow can route a
floored change on a non-empty `"floored_by"` (for example, hold it for an
owner's approval) rather than return it to be split.

Every report also carries `"triggers"`: one entry per consequence whose floor
is High, sorted by class, `[]` when none. Each names its `class`, the `paths`
and `types` that are its evidence, and `"why"` it is High: `class` (the
built-in class's own floor), `repo_class` (the repo class's own floor) or
`production_root` (a production root raised a lower floor). The Markdown lists
them under "Triggers", or states that none fired and the level cannot be High.
Triggers are the contract a gate keys on: with the shape level capped at
Medium, a change is High if and only if `"triggers"` is not empty, so a gate
(a lane's land-ready check, an owner's approval) tests `triggers`, for example
`jq -e '.triggers == []'`, not `level`, `floored_by` or the floors, and names
each trigger's evidence when it holds a change. The same result always prints
the same bytes.

## With satelle

With [satelle](https://github.com/bobmcallan/satelle), a story carries its
riskelle estimate from planning, which the developer and the agent work down,
and its actual score from the real diff; a High estimate is sent back to be
split. riskelle itself knows nothing of satelle: the wiring below is a few
shell commands (they need `jq`) and one coded satelle gate.

**Install.** Copy `integrations/satelle/riskelle-risk-review.md` into the
repo's `.satelle/skills/`, then add its gate to the workflow beside satelle's
own `satelle-estimate-actual-review` gate (keep that one too):

```toml
[[gate]]
skill = "riskelle-risk-review"
on = ["in_progress", "<last state before the branch lands>", "done"]
for = ["*"]
```

and run `satelle workflow validate`.

**Tags.** The figures sit in the story's tags, next to satelle's own
`estimate-*` and `actual-*`:

| Tag | Holds |
| --- | --- |
| `estimate-risk:<total>` | the estimate's total, 0-100 |
| `estimate-risk-level:<level>` | the estimate's level: low, medium or high |
| `actual-risk:<total>` | the real diff's total, 0-100 |
| `actual-risk-level:<level>` | the real diff's level |

**Estimate at planning**, before requesting `plan → in_progress` (re-run it
whenever the plan changes; it replaces the previous figure):

```sh
riskelle estimate plan.json > risk-estimate.json
satelle story set <id> --remove-tags estimate-risk:,estimate-risk-level:
satelle story set <id> --add-tags "estimate-risk:$(jq .total risk-estimate.json),estimate-risk-level:$(jq -r '.level|ascii_downcase' risk-estimate.json)"
satelle story attach <id> --name risk-estimate --type output --file risk-estimate.json
```

**Actual before it lands**, in the story's tree, before the branch merges into
the target (once it has landed, the merge base is the head and the diff is
empty):

```sh
riskelle score --base <target> --head HEAD > risk-actual.json
satelle story set <id> --remove-tags actual-risk:,actual-risk-level:
satelle story set <id> --add-tags "actual-risk:$(jq .total risk-actual.json),actual-risk-level:$(jq -r '.level|ascii_downcase' risk-actual.json)"
satelle story attach <id> --name risk-actual --type output --file risk-actual.json
```

The attached reports keep the riskelle version and rules hash behind each
figure.

**A High estimate** is refused at `in_progress` until the story is split. The
one exit is a developer's decision, taken from their own terminal (satelle
refuses it from an agent session):
`satelle story waive <id> --gate riskelle-risk-review --check high-estimate --reason "..."`.
The gate reads that waiver from its payload and records it in its verdict
notes; no other check of the gate can be waived.

The gate's exact behaviour on each edge, including the estimate-beside-actual
line it leaves for reviewers, is in the skill file itself.

## Rules

- **Built in, versioned with each release:** the measures, weights, bands,
  consequence floors (`consequence_floors`), the shape cap (`shape_cap`), the
  built-in production environment names (`prd`, `prod`, `production`) and
  default patterns. Changed only by a riskelle release, so the scale is the
  same everywhere; a repo may add production environment names, never remove
  one.
- **`.risk/rules.json` in the assessed repo:** settings that can only *add*
  risk or context (extra generated paths for the report, extra sensitive
  areas, the exclusion toggles `exclude_non_code_files` and
  `exclude_log_files`, `production_roots`, `consequence_classes` and
  `production_environments`). It is read from the **target branch**, so a change cannot alter its
  own rules. Anything that would lower a score is refused by name. A change
  that edits `.risk/` is scored like any other change: riskelle does not try
  to guard against a dishonest developer. riskelle's own
  [`.risk/rules.json`](.risk/rules.json) is an example: it adds areas for the
  scorer and the release pipelines, and marks the report goldens generated.

Production roots in `.risk/rules.json`, such as
`{"production_roots": ["prod-tenant/**"]}`, raise the floor of a consequence
under them to High (see [Consequences](#consequences)). A root that is empty,
absolute or does not end in `/**` is refused by name; roots with no consequence
in them change nothing.

Production environments in `.risk/rules.json`, such as
`{"production_environments": ["live"]}`, add job environment names that
`production_deploy` treats as production, beside the built-in `prd`, `prod`
and `production` (see [Consequences](#consequences)). An added name matches as
a built-in one does: ignoring case, alone or followed by a non-letter
(`live-aue`). Names are only added: nothing removes a built-in name, and an
empty list changes nothing. An empty name, or an entry that is not a string,
is refused by name.

Repo consequence classes in `.risk/rules.json`, such as
`{"consequence_classes": {"release_guard": {"paths": ["scripts/plan-guard-allow*"], "floor": "Medium"}}}`,
floor a change to a file the repo knows is consequential (see
[Consequences](#consequences)).

The exclusion toggles in `.risk/rules.json`:

- `exclude_non_code_files` covers the non-code catalog: repo and editor
  config, config formats, data, and agent and harness config.
- `exclude_log_files` covers the run-record catalog (see
  [Run records](#run-records)): logs, plan output and state snapshots.
- Both are `true` by default: those files then leave size and degree, and
  always count for spread. Being non-code, they never count as untested.
- Setting one to `false` counts those files for size and degree, so it can
  only add risk. `true`
  is accepted as the default; any other value is refused by name.
- There is no toggle for test files: test lines never count toward size or
  degree.

Every report records the riskelle version, the rules hash and the value of
each exclusion toggle it was scored with.

### Run records

Paths that record a change rather than make it (logs, plan output, state
snapshots) are classed `run_record` in the facts `"classes"`, by the built-in
catalog below, owned by `internal/facts/classes.go`. Patterns are case-sensitive
globs over the repo-relative path: `**/` matches any directories, `*` any
characters but `/`, and `?` one such character.

| Group | Patterns |
| --- | --- |
| Logs | `**/*.log` |
| Rotated logs | `**/*.log.0*`, `**/*.log.1*`, `**/*.log.2*`, `**/*.log.3*`, `**/*.log.4*`, `**/*.log.5*`, `**/*.log.6*`, `**/*.log.7*`, `**/*.log.8*`, `**/*.log.9*` |
| Log directories | `**/logs/**`, `log/**` (repo root only, so source packages such as `internal/log` are not run records) |
| Package-manager debug logs | `**/npm-debug.log*`, `**/yarn-error.log*`, `**/yarn-debug.log*`, `**/pnpm-debug.log*`, `**/lerna-debug.log*` |
| Terraform plan output | `**/*.tfplan`, `**/tfplan`, `**/*.tfplan.json`, `**/tfplan.json`, `**/*.tfplan.txt`, `**/tfplan.txt` |
| State snapshots | `**/*.tfstate`, `**/*.tfstate.*` |

Tenant and other snapshots have no shared naming convention, so they are not in
the built-in catalog.

### Sensitive areas

The built-in sensitive areas are owned by `internal/facts/areas.go` and use the

adds patterns or areas; it never replaces the built-in ones.

| Area | Patterns |
| --- | --- |
| auth | `**/auth/**`, `**/oauth/**`, `**/*Auth*/**`, `**/*Auth*.cs`, `**/auth.*`, `**/auth_*`, `**/*_auth.*`, `**/identity/**`, `**/*Identity*/**`, `**/jwt*`, `**/*Jwt*`, `**/*Token*.cs` |
| infrastructure | `**/*.tf`, `**/*.tfvars`, `**/*.bicep`, `**/*.bicepparam`, `**/azuredeploy*.json`, `**/terraform/**`, `**/infra/**`, `**/infrastructure/**`, `**/k8s/**`, `**/kubernetes/**`, `**/helm/**`, `**/Dockerfile`, `**/Dockerfile.*`, `**/*.dockerfile`, `**/docker-compose*.yml`, `**/docker-compose*.yaml`, `.github/workflows/**`, `azure-pipelines*.yml`, `azure-pipelines*.yaml`, `.azuredevops/**`, `pipelines/**/*.yml`, `pipelines/**/*.yaml`, `.pipelines/**/*.yml`, `.pipelines/**/*.yaml`, `.circleci/**`, `.buildkite/**` |
| migrations | `**/migrations/**`, `**/Migrations/**`, `**/migrate/**`, `**/*.sql` |
| secrets | `**/*secret*`, `**/*Secret*`, `**/*secret*/**`, `**/*Secret*/**`, `**/*.pem`, `**/*.key`, `**/*.pfx`, `**/*.p12`, `**/*.jks`, `**/*.keystore`, `**/id_rsa*`, `**/id_ed25519*`, `**/.env`, `**/.env.*`, `**/crypto/**`, `**/*Crypto*`, `**/*Encrypt*` |

`pipelines/` and `.pipelines/` count only their YAML (pipeline definitions), as
"pipelines" is an ordinary directory name; `.circleci/` and `.buildkite/` are

## Where it runs

- Locally, by developers and coding agents.
- Azure DevOps pipelines and GitHub Actions, posting a PR status and one summary
  comment kept up to date (GitHub: see [GitHub pull requests](#github-pull-requests)).
- Results go to a ledger keyed by developer, from which the KPI (share of low
  risk changes, alongside volume) is reported per period with the rules pinned
  for that period.

### GitHub pull requests

The action in `action.yml` scores every pull request with a **released**
riskelle, installed by that release's own `install.sh` (the developer install:
the latest release by default, as `curl | sh` installs it, or the tag in the
action's `version` input, checked against the release's checksums file, never
built from the PR), posts a `riskelle` commit status on
the PR head, and keeps one summary comment on the PR, updated in place on each
push. riskelle's own `.github/workflows/riskelle.yml` runs it and is the
workflow to copy. The repository is public, so installing needs no token.

To adopt it in a repository:

1. Copy `.github/workflows/riskelle.yml` to `.github/workflows/` and replace
   `uses: ./` with `uses: bobmcallan/riskelle@vX.Y.Z`. The `version` input is
   optional: left out, it is `latest`; set it to a tag (v0.19.0 or later, the
   first release with `install.sh`) to pin the scale. Keep its permissions (`pull-requests: write` and
   `statuses: write` for the default token, which posts the status and the
   comment), `fetch-depth: 0` (the merge base, branch age and trunk drift need
   history) and its concurrency group.
2. Inputs (`version`, `token`, `repository`) and outputs (`total`, `level`) are
   described in `action.yml`.

On the pull request:

- The `riskelle` status reads `<Level> · <total> / 100` and links to the
  summary comment. It is always `success`: the score is a measure, not a merge
  gate (a branch rule can still require the status). It is `error`, linking to
  the run, when riskelle cannot score; the comment is then left as it was.
- The summary comment is the `riskelle score --format markdown` report behind a
  hidden `<!-- riskelle:summary -->` marker. Duplicate marked comments are
  deleted; other comments are never touched.
- The base is the target branch's tip and the head is the PR head commit (not
  GitHub's merge commit), both named in full on the report, so
  `riskelle score --base <base> --head <head>` with the release the report
  names reproduces it locally byte for byte. The rules are read from the target branch.

Pull requests from forks are not supported: their token cannot post.

### Azure DevOps

[`ado/riskelle.yml`](ado/riskelle.yml) is a job template that scores every
pull request with a released riskelle, installed by that release's own
`install.sh`: the latest release by default, or the tag in the template's
`version` parameter (v0.19.0 or later) to pin the scale.
The repository is public, so installing needs no token. Its parameters and the
permissions it needs are documented in the template's header comments. To
adopt it:

1. Reference the template from your pipeline, at the same release tag you run.
   Through a GitHub service connection (`riskelle-github` here):

   ```yaml
   resources:
     repositories:
       - repository: riskelle
         type: github
         endpoint: riskelle-github
         name: bobmcallan/riskelle
         ref: refs/tags/vX.Y.Z

   jobs:
     - template: ado/riskelle.yml@riskelle
   ```

   Add `parameters: { version: vX.Y.Z }` to pin the release.

   Or copy `ado/riskelle.yml` into your repository and use
   `- template: ado/riskelle.yml`, optionally with a `version` parameter.
2. Make the pipeline run on pull requests: on Azure Repos, add it as a
   **Build validation** policy on the target branch (the job is skipped on any
   build that is not for a pull request).
3. Grant the project's build service identity **Contribute to pull requests**
   on the repository, so the job can post the status and the comment.

Each pull request build then gives:

- a PR status `riskelle/score` whose description carries the band and total
  (`Low, 7/100`). It is `succeeded` for every band (riskelle measures, it does
  not gate) and `error` when the change could not be scored;
- one summary comment, the Markdown report, updated in place on every push;
- the JSON report as the build artifact `riskelle`.

The pipeline scores the PR's own head commit against its target branch tip,
not the merge commit ADO builds, so the result is what you get locally. To
reproduce it, run the release the report names with the `base` and `head`
SHAs from the report: `riskelle score --base <base> --head <head>`.

Self-hosted agents need Linux (amd64 or arm64) with bash, git, curl, jq, tar
and sha256sum, as Microsoft-hosted Ubuntu agents have.

## Releasing

A release is cut by pushing a `vX.Y.Z` tag on a commit on `main`:

```sh
git tag -a vX.Y.Z origin/main -m vX.Y.Z
git push origin vX.Y.Z
```

The tag runs `.github/workflows/release.yml`. It builds every target with
`scripts/release.sh` (the owner of the target list and archive layout), checks
that the linux/amd64 binary reports the tag as its version, and attaches the
archives, `riskelle_vX.Y.Z_checksums.txt` and `install.sh` (the installer,
served at `releases/latest/download/install.sh`) to a GitHub Release named
after the tag. A tag whose commit is not on `main` fails the run. A pushed tag is
never moved: a broken release is fixed forward with the next patch version.
Once the Release is published, the workflow's `pages` job publishes this README
as the project site at https://bobmcallan.github.io/riskelle/.

Verify a download:

```sh
sha256sum -c --ignore-missing riskelle_vX.Y.Z_checksums.txt
```

Reproduce a release on Linux: `git checkout vX.Y.Z && scripts/release.sh vX.Y.Z /tmp/out`,
then compare the checksums file with the one on the Release. The Go toolchain
is pinned by `go.mod` and every timestamp is the commit time, so the archives
match byte for byte.
